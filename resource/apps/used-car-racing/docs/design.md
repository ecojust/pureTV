# 极品二手车：设计与物理说明

## 比赛结构

每场固定六个车位，支持一至两名真人，其余为电脑车手。玩家先在检车台阅读随机车型、动力和车况，再进入赛道。相同随机种子用于复现模型测试；正式游玩产生新的抽取结果。

车辆造型、赛道、品牌呈现和音效均为原创。六类车身分别对应紧凑车、轿车、跑车、旅行车、肌肉车和拉力车，不使用真实车厂标识。三条道路使用同一米制中心线数据供动力学、AI 路径和三维路面绘制，减少画面与物理边界不一致。

## 输入与虚拟力

手机转向区域提供连续的 -1 至 +1 输入；油门和刹车采用大面积触区。赛中 SELECT 短按切换追车／引擎盖镜头；低于 1.2 m/s 时长按约 0.8 秒切换 D/R，再通过油门驱动。刹车按住后模拟踏板力逐步上升，释放时快速回落。普通手机触摸输入不提供可靠的真实力值，因此 N 是游戏中的虚拟力单位。

### 虚拟摇杆与姿态转向

虚拟摇杆默认启用，可完全在局域网内使用。可选的陀螺仪模式读取手机姿态，将首次有效的舒适握持姿态设为中立；约 45° 达到最大转向，中心保留小死区并平滑输入。姿态转向只应用于倒计时和比赛；车库仍保留滑动选赛道。运动权限拒绝、缺少有效数据时回退到摇杆，姿态中断、失焦和平放时释放方向与踏板，并在恢复后重新校准。

普通局域网 HTTP 页面通常不能访问运动传感器。手柄因此通过明确点击打开固定 HTTPS 页面 `https://ecojust.github.io/pureTV/controller/used-car/0.1.1/`，在安全的顶层页面中请求权限。该页面首次加载需要互联网；电视端及虚拟摇杆不依赖它。

HTTPS 页面使用严格校验来源、窗口和随机通道标识的 `postMessage`，将输入交给原局域网页面持有的 WebSocket。房间与通道信息只放在 URL fragment 中，加载后从地址栏清除，不作为静态站请求参数。桥接只转发允许的控制帧，回执超时或过期输入触发释放，不使用公网输入中继或混合内容豁免。移动浏览器可能暂停后台的局域网页面，因此这条路径仍需真机验证；不可将浏览器模拟姿态测试等同于所有手机可用。

静态站由 `tools/build-controller-site.py --output <目录>` 构建，只导出五个控制器文件。每个已发布版本保存在自己的路径；历史内容从对应发布标签读取，同一版本的文件变化会拒绝构建，避免旧 APK 的控制器被新版本覆盖。桥接脚本的版本常量、发布路径和子页面识别必须与 Gradle／发布标签版本一致；仅修改应用版本而遗漏控制器路径也会拒绝构建。输出清单记录来源提交和文件 SHA256；站点不包含 APK、签名材料或其他仓库资源。

脆弱刹车踏板的断裂阈值为 1600 N。达到阈值即触发不可逆的本场故障，松开、暂停、重连均不能修复；下一场比赛重新生成车况。正常车辆不会因这个特定阈值断裂。故障与当前受力应同时显示，避免玩家只能通过失控猜测车辆状态。

## 动力学边界

车辆模型采用小固定步长的平面动力学，结合低速响应、前后轮侧偏力、摩擦圆抓地力约束与载荷转移。发动机和自动变速箱驱动车轮，空气和滚动阻力消耗速度；路面、坡度、温度与车况改变响应。AI 使用相同车辆状态与赛道数据。

模型侧重让刹车距离、弯道极限、转向迟滞及车辆差异可感知。它是有明确参数与可重复测试的游戏模型，未经过真实车辆遥测标定；不应把展示的踏板力、抓地力或极限速度视为实际车型测量结果。屏幕车身侧倾与悬挂表现用于反馈模型状态，并非完整四轮多体悬挂求解。

## 渲染与兼容

场景使用本地 Three.js r124（WebGL 1）渲染。道路几何、地形、建筑及车辆模型由项目代码生成，无需联网加载地图。手机和电视的房间通信只在局域网进行。

### 0.1.1 材质与场景

车辆合批保留 UV，车身面使用投影坐标，轮胎和灯组采用适合各自表面的贴图坐标。颜色贴图采用 sRGB，法线和高光数据采用线性空间；贴图使用 mipmap，并将各向异性过滤限制在设备能力与上限之内。不同车辆共享图片和静态环境立方体，重新抽车只释放车辆自己的几何和材质，不释放仍被其他车辆使用的共享图片。

道路沥青、岩石及车辆图集颜色贴图为 1024²，其余环境颜色贴图为 512²，法线与高光遮罩为 256–512²。车辆图集包含带边缘延拓的车漆、橡胶、灯罩和织物四格，不透明车身和每个车轮合批后仍通过顶点材质参数保留各自的高光、反射和发光响应。沥青、混凝土、岩石、砂土、草地、外墙、集装箱、光伏板、车漆、橡胶、灯罩、织物和枝叶由本项目离线生成。原创贴图及其生成脚本使用 MIT，见[素材声明](../src/main/assets/TEXTURE-LICENSE.txt)。重新生成需 Python 3、Pillow 和 NumPy，在仓库根目录执行：

```sh
python3 tools/generate-used-car-textures.py
```

连续的不规则山脊和岩石轮廓由少量顶点构成，枝叶以透明裁切贴片形成。场景使用共享颜色／法线／高光纹理、顶点颜色、雾及静态环境反射增强层次，不启用实时反射捕获、SSAO 或全屏泛光。贴图像素预算只估算图片与 mipmap 占用，不代表驱动分配、帧缓冲和全部运行时内存。

### 合批前后绘制次数

同一台 Chromium / ANGLE SwiftShader 环境，使用 960×540、六款车型、固定车辆位置与追车镜头比较图集合批前的提交 `e1ce37522542b21d4386cb0bd1ba9597c9bc953d` 和本次合批实现。每组预热 3 帧、采样 8 帧；双人列为两视图合计。

| 场景 | 单人：合批前 → 后 | 双人：合批前 → 后 |
|---|---:|---:|
| 霓虹港湾 | 218 → 104 | 403 → 195 |
| 云脊公路 | 214 → 99 | 391 → 181 |
| 落日能源环线 | 214 → 99 | 395 → 185 |

这些固定场景的绘制调用减少约 52–54%，三角形数增加约 0.2%，连续帧的 GPU 资源计数保持稳定。它衡量的是提交次数和资源复用：材质图集的着色器也增加了分支工作，软件渲染耗时并非全部下降，不能据此推导电视帧率提升比例或声称实机已流畅。

可选对比工具只读取本地已有的基线提交，不联网拉取历史，也不作为日常 CI 的历史依赖：

```sh
node resource/apps/used-car-racing/tests/performance.mjs \
  --baseline e1ce37522542b21d4386cb0bd1ba9597c9bc953d \
  --output /tmp/puretv-used-car-performance
```

输出 `performance.json`、日志和相同场景的前后截图。记录的 `renderSubmissionWallMs` 是 JavaScript `render()` 的墙钟时间，可能包含驱动等待，不是 GPU 执行时间或硬件 FPS。

本次更新不改变中心线路径、车辆参数、故障阈值或比赛规则。性能验证需要同时检查单人、双人分屏、赛道切换、抽车时的资源释放与 WebGL 上下文恢复，不能只凭单张截图判断。

Chrome 61 / ES2017 语法检查用于发现新语法依赖；现代 Chromium 软件渲染用于检查实际三维路径、截图和生命周期。二者都不能替代真实旧 Android WebView、电视 GPU 和手机网络延迟测试。
