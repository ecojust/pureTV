# 压力封装 / Pressure Seal

操控带有余热的封装机，让压力依次稳定在三种材料要求的范围内。加热、松手、泄压都需要把握时机：松开加压后，余热仍可能让压力继续上升。

这是 pureTV 百款游戏计划的第 40 款设计，包名 `com.ecojust.pressuresealtv`，版本 `0.1.0`。一人游玩，支持电视遥控器、键盘和局域网手机手柄。只有完成验证并推送的版本才计入计划完成数量。

## 操作

- 按住 A：加热并加压。键盘使用 Space、Z，或游戏中的 Enter。
- 按住 B：打开泄压阀。键盘使用 X 或 B。
- 手机右侧整个三分之一区域分成上下两半：上半区 A，下半区 B，可同时按住。A+B 会同时加热加压和泄压，余热很高时压力仍可能上升。
- 左右方向或手机摇杆在菜单中选择“起步、换压、高压”；游戏中方向不改变设备或目标。
- P、Escape、START 或独立暂停按钮：暂停/继续。R 或手机 SELECT：重新开始。菜单中的 B 切换声音。

暂停会冻结压力、余热、热损伤和保持计时。继续后先真实松开仍按住的按钮，再进行新的操作。取消输入只会撤销控制；未暂停时，设备仍会自然冷却、泄漏并继续计算压力。

## 密封规则

每组任务依次处理三件包装。压力必须在当前材料的目标区间内连续保持指定时间；离开区间会清空本次保持进度。刚从外面进入区间的那个物理步不会直接获得整段保持时间。完成后自动切换下一件，压力和余热保留，新材料的热损伤与保持计时从零开始。

压力达到 **110 kPa** 会爆裂。余热超过材料的安全值时会累计热损伤，达到该材料的上限也会失败。冷却或泄压不会修复已累计的损伤。同一步发生失败与密封完成时，先判失败；爆裂优先于过热。

| 任务 | 第一件 | 第二件 | 第三件 |
| --- | --- | --- | --- |
| 起步 | 金属膜 22–38 kPa，6 秒 | 纤维层 46–62 kPa，6.5 秒 | 薄封膜 70–86 kPa，7 秒 |
| 换压 | 纤维层 42–56 kPa，6.5 秒 | 金属膜 20–34 kPa，6.5 秒 | 薄封膜 58–72 kPa，7 秒 |
| 高压 | 薄封膜 66–80 kPa，7 秒 | 金属膜 36–50 kPa，7 秒 | 纤维层 78–92 kPa，7.5 秒 |

三组任务使用相同规则，改变材料顺序和压力要求。没有额外超时失败。HEAT 是游戏中的 0–100 归一化余热值，不是摄氏温度。金属膜、纤维层、薄封膜的安全余热分别为 68、62、58，热损伤上限分别为 90、105、120 HEAT·秒。

## 画面与公开规则

画面以带金属法兰、密封圈和观察窗的压力舱呈现设备，分别显示当前压力、目标范围、连续保持时间、余热、安全余热线和热损伤。A/B 工作状态与余热分开显示；松手趋势提示表示下一步不按 A/B 时的压力方向。弹窗使用共享界面的毛玻璃背景。

- [公开设计](docs/public-design.md)：材料、任务、操作和呈现要求。
- [模型规则](docs/model-contract.md)：50 毫秒物理步、压力/热量公式、输入取消、保持判定与结算顺序。
- [观察接口](docs/public-interface.md)：真实观察、完整调用记录与稀疏截图/录像的验证范围。

游戏使用共享 Android 宿主、局域网手柄和 WebGL 批处理渲染器。材质、光照与静态细节在本地烘焙到一张图集；实际绘制次数与运行时开销以发布报告中的测量结果为准。

## 构建与验证

在仓库根目录执行：

```sh
python3 resource/game-kit/build.py \
  --game resource/apps/pressure-seal \
  --output /workspace/scratch/hundred-games/pressure-seal/build
```

`game-config.json` 和 `assets-index.json` 由构建工具生成。`game.json` 的 `actions: 2` 让手机右侧两片触控区分别控制 A/B。

发布产物使用 `pressure-seal-0.1.0.apk` 和 `docs/gameplay-0.1.0.mp4`。每个文件须小于 10,000,000 字节；源码、签名、验证、录像和画面审阅结论分别记录在对应的 `docs/verification.json`、`docs/signing-receipt.json`、`docs/gameplay-0.1.0.json`、`docs/art-review.json` 中。

完整模型调用记录与浏览器证据分开记录：前者保存每次真实调用的前后状态，后者验证实际界面、键盘和手柄页面。稀疏截图与录像不用于补造漏掉的物理步骤。浏览器软件渲染结果不代表实体电视或手机性能；未使用实体硬件时，报告明确注明未做硬件验证。
