# Recover only failed read transports within the original menu deadline

The original v2 diagnostic, run `44642922231` at `0415846f`, successfully attached the startup console and observed 29 menu steps. At original step 33, the one SDK A tap was held for about 16 ms and both messages received unique ACKs. A single graphics GET then closed after 10.003 seconds. The driver failed immediately even though the unchanged step allowed 240 seconds. Its final new GET subsequently observed the actual Finland query, `phase=intro`, one frame and poll count 20. This was a diagnostic transport failure during loading, not a reproduced black race scene. The complete original failed evidence remains unchanged in `android-graphics-diagnostic-44642922231/`.

Only the separate graphics diagnostic driver and its existing test file change. `menu_graphics` follows the original QA reader's transport policy: at most three new GETs, at most fifteen seconds per request and at most forty-five seconds for the read operation, further bounded by the original step's absolute deadline. It retains this driver's 512 KiB body limit and per-request raw HTTP outcome log. Failed transports and recovery attempts are also recorded in the existing report, with no new export path.

Only connection closure/reset/abort/refusal, timeout, or a URL error wrapping one of those transports may retry. HTTP responses reporting errors, malformed JSON, oversized bodies and actual Observer/game errors remain failures. Each retry calls the HTTP reader again; an earlier successful snapshot is never returned. The code neither sends SDK input nor resets the menu deadline. The existing 240-second limit, exact menu predicates, ownership/release checks and two subsequent fresh-poll confirmations are unchanged. The source comparison confirms that the menu method differs only at its read call.

Validation used an isolated small checkout of the exact `0415846f` parent, overlaying only the two proposed files. All other imported local modules, including `qa-plan.py`, and the two prior v7 fixtures came from that parent, excluding concurrent Windows QA changes. Fifteen tests passed, including real local TCP/HTTP connections that close without a response and then return different fresh JSON, three-attempt exhaustion, a shorter original deadline, and immediate rejection of HTTP/JSON/body-budget/game errors. This is host-side transport validation, not Android or graphics testing. No game clock or model is changed by these tests.

No original common runner, Java Observer, production host, game asset, APK or signing code changed. The original v2 failure is preserved. No new native run, signing or workflow dispatch occurred during this fix.
